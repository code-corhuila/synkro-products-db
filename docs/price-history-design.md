# Product price history: design

Status: design first. The tests in `tests/test_price_history.py` were written
before the migrations; see [evidence](evidence/price-history-tdd.json) for what
was and was not actually executed.

## Why

`PUT /api/v1/products/{id}` changes `product.price_cents` in place, so the
previous price and the person who changed it are lost. Price is the one column
whose change has financial consequences, so each change must be an auditable
fact: which product, from what, to what, by whom, when.

Pattern: an **append-only audit table** (event log) next to the aggregate's
table, written in the same transaction as the change. The table is the
database half of a Repository + Unit of Work in the API: the row is inserted
only if the price update commits, and never otherwise.

## The table

`products_schema.product_price_history`, one row per price change.

| Column | Type | Rule |
|---|---|---|
| `history_id` | `UUID` | primary key `pk_product_price_history`, generated by the application (UUIDv7, like every id here: no `DEFAULT`) |
| `product_id` | `UUID NOT NULL` | `fk_product_price_history_product` → `product(product_id)`, `ON DELETE RESTRICT ON UPDATE RESTRICT` |
| `sequence_no` | `BIGINT NOT NULL` | `chk_product_price_history_sequence_positive` (`>= 1`) |
| `old_price_cents` | `BIGINT NOT NULL` | `chk_product_price_history_old_price_positive` (`> 0`, as `product.price_cents`) |
| `new_price_cents` | `BIGINT NOT NULL` | `chk_product_price_history_new_price_positive` (`> 0`) |
| `changed_by` | `UUID NOT NULL` | the verified user id from the token. Cross-domain (Auth owns users): no foreign key, as `stock_adjustment.adjusted_by` |
| `changed_at` | `TIMESTAMPTZ NOT NULL` | an instant, supplied by the application in UTC. No `DEFAULT`: the writer states it explicitly |

Plus `chk_product_price_history_price_changed` (`old_price_cents <> new_price_cents`:
a row exists only for a real change) and
`uq_product_price_history_product_sequence` (`UNIQUE (product_id, sequence_no)`).

### Ordering: a sequence, not a timestamp

Events of one product are ordered by `sequence_no`, 1, 2, 3…, assigned by the
API while it holds the product row lock (`SELECT … FOR UPDATE`), as
`coalesce(max(sequence_no), 0) + 1`. Ordering by `changed_at` or by
transaction time would be wrong: two transactions can take their timestamps in
one order and commit, or acquire the lock, in the other, and equal timestamps
are possible. The unique constraint makes a duplicate position impossible even
if a writer forgets the lock: the second insert fails instead of producing an
ambiguous order. The timestamp is information, not the order.

### Foreign key RESTRICT

History is evidence. Deleting a product that has history must fail
(`23503`), not cascade. `product` rows are never deleted by the API (soft
delete), so RESTRICT costs nothing in normal operation. The key stays inside
`products_schema`, in keeping with the one-schema-per-domain rule.

### Index

`idx_product_price_history_product_sequence` on `(product_id, sequence_no DESC)`
serves `GET /products/{id}/price-history` (newest first, paginated). The unique
constraint's own index is `(product_id, sequence_no)` ascending and a btree can
be scanned backwards, so the query would also work without this index: it is
kept as an explicit, separately named index so the access path of the read
model is stated, and survives a later change to the unique constraint. Cost
accepted: one more index to maintain on an append-only table with low write
volume.

## Append-only privileges

`V003` grants `products_writer` `SELECT, INSERT, UPDATE` on every table a
migration creates, through `ALTER DEFAULT PRIVILEGES`, and `V020` grants
`products_reader` `SELECT` the same way. A new table therefore inherits
`UPDATE` for the writer, which is wrong for an audit table.

`V024` revokes, on this table only:

- `products_writer`: `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`
  → effective `SELECT, INSERT`. `products_app` is a member of
  `products_writer`, so it has exactly those two.
- `products_reader`: everything but `SELECT` (explicitly granted, so it does
  not depend on the default).

The default privileges themselves are **not** changed: the other tables keep
what `V003` gives them. Cost accepted: privileges stop the application role,
not the table owner or a superuser; protection against the owner would need a
trigger, which is out of scope. Every future table created by the migration
creator still inherits `UPDATE`; a future audit table must repeat the revoke.

## Migrations

| Version | Location | Purpose |
|---|---|---|
| V021 | `01_ddl/03_tables` | create the table with its named `PK`, `CHECK` and `UNIQUE` constraints |
| V022 | `01_ddl/04_alter` | `fk_product_price_history_product`, `RESTRICT` |
| V023 | `01_ddl/10_indexes` | `idx_product_price_history_product_sequence` |
| V024 | `03_dcl/01_grants` | append-only privileges |

Each has a mirrored `U021..U024__*.rollback.sql` under `05_rollbacks`.
`V001..V020` and `U001..U020` are not edited. Rollbacks run highest first:
`U024` restores the table's default privileges, `U023` drops the index, `U022`
drops the key, `U021` drops the table. Applied to a database holding history
rows, `U021` destroys them: the rollback is for disposable environments and
recovery before any history exists; it is not a data-preserving downgrade.

## Tests

`tests/test_price_history.py`, in the same real-engine style as
`tests/test_approved_integrity.py` (real PostgreSQL 16 and Flyway through the
Docker CLI, disposable containers, `PRODUCTS_TEST_DISPOSABLE=1`):

- clean install: columns, every named constraint, `RESTRICT` actions, index;
- real SQL violations with the expected SQLSTATE **and constraint name**, each
  next to a valid control;
- privileges: exact effective sets for `products_writer`, `products_app` and
  `products_reader` on the history table, the other tables unchanged, the
  default ACL unchanged, and real `permission denied` (`42501`) for `UPDATE`,
  `DELETE` and `TRUNCATE` as the writer;
- upgrade from a populated V020 database: existing rows are byte-identical, the
  history is empty, only history objects were added, a second migrate is a no-op;
- rollback `U024..U021` then re-apply restores the same structure, without
  touching other tables' rows or privileges.

`db-ci.yml` runs this suite, and its table-privilege step no longer hardcodes
`SELECT, INSERT, UPDATE` for every table: the history table is expected to be
`SELECT, INSERT` only.

## Out of scope

The Products API's use of the table (transaction, locking, endpoint) is
designed in `synkro-products-api`. The domain documentation in
`synkro-docs` (`06-data/models.md`) is updated separately: the table described
here is not yet reflected there.
